# Valkey acceleration keeps a shared PostgreSQL ceiling

Valkey accelerates operational rate refusal, while every admitted request consumes the same PostgreSQL counter used by fallback replicas. Independent healthy and fallback budgets could exceed the limit during a partial partition; retaining one ceiling makes cache loss, ambiguous replies and split connectivity restrictive instead of granting extra capacity. This deliberately retains a PostgreSQL write for admitted requests and does not claim financial or scientific authority for Valkey.

The adapter uses redis-rs 1.8 with nonblocking Tokio/Rustls, scripts and a bounded multiplexed connection manager. The client supports Valkey; its MSRV 1.88 is below the workspace toolchain. Fred 10.1 also supplies Tokio/TLS/pooling and topology support, but the narrower multiplexed client fits these nonblocking single-key commands without a second pool. Cluster/sentinel deployment is not configured or verified by this choice. Client API/version evidence and the comparison are recorded in the implementation handoff; see [redis-rs](https://github.com/redis-rs/redis-rs) and the [pinned source](https://docs.rs/crate/redis/1.8.0/source/Cargo.toml).
