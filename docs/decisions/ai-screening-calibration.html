How do we calibrate the AI second reviewer?

Today the AI screens records on its own only after a passing, hash-matched, expert-adjudicated calibration bundle exists. Nothing in the product can create one, so the screening pages show the “AI is paused” banner. This document explains the gate, compares five ways to open it, and lists what you need to decide.

Short version
  • The gate is intentional and well built on the checking side, but there is no way to create a bundle in the app, and the hash is so strict that any Rust source change invalidates a calibration.
  • Recommended: shadow-mode warm-up (the AI silently second-screens the first records the humans decide, metrics accumulate, you approve), plus continuous monitoring. No extra human screening.
  • Before any of that, two small code decisions matter more than the statistics: what the “runtime” part of the hash covers and per-stage bundles. See section 1.

Everything in section 1 comes from reading the code in this worktree; nothing was run. Statistics in section 3 were computed for this document (exact binomial intervals). Time estimates are assumptions and are labelled as such.

1. What the gate requires today, and why

The AI’s autonomy level for title/abstract and full-text screening is “second reviewer”. Whether it actually runs unprompted depends on one more check.

Why it exists

ADR 0004 (docs/adr/0004-compiled-review-definition-seam.md) says automation-triggered consequential runs “require an immutable, passing calibration bundle whose semantic-bundle hash exactly matches the compiled manifest”, and that the small checked-in evaluation set “cannot authorize production automation”. The PR15 acceptance note (docs/acceptance/pr15-evals-hardening.md) repeats it: consequential automation stays disabled until an expert-adjudicated bundle is persisted for the project and exact hash. Reviewer-requested suggestions (the user clicks “ask AI”) are not gated. The AI never writes scientific state either way; it produces proposals and opinions.

How a record reaches the AI automatically

  1. Stage is set to “second reviewer”Autonomy level resolved per project and task (resolve_autonomy_level).
  2. The worker sweep finds a passing bundleOnly projects that have a row in review_calibration_bundles with status='passing' are swept at all (crates/postgres/src/second_review.rs). The newest by evaluated_at is used. Projects without one cost one query and get no work.
  3. It picks up to 5 waiting records per project per tickRecords with no human decision yet and no AI decision; one attempt per record, stage and protocol version (second_review_attempts, migration 0040). Stops when the project’s AI budget is spent.
  4. Admission compares hashesThe run’s freshly built manifest must have the same semantic_bundle_hash as the bundle, and the bundle must be passing (admit_calibration in review_calibration.rs, called from review_runs.rs). Otherwise: calibration_missing, calibration_failed or calibration_stale.
  5. On refusal the sweep stops and records whyA stale refusal is written to second_review_gate; the API reports needs_calibration or calibration_stale; the web banner second-review-paused appears (ScreeningViewSwitch.svelte).
  6. Result is an opinion, not a decisionStored in ai_reviewer_decisions (migration 0029). If it differs from the human, it is a conflict a person resolves.

Findings you should know before choosing

Blocker A. Nothing can create a bundle

insert_review_calibration_bundle exists (review_calibration.rs) and is exported, but only tests call it. There is no HTTP route, no CLI, no worker job, no UI. The banner tells users to “ask the person who runs this DeepRef deployment”, who in practice would need raw SQL.

Rows are immutable (an update trigger rejects changes, migration 0022); correction means inserting a new row.

Design risk B. Any code change invalidates calibration

The “runtime” input is DEEPREF_SEMANTIC_BUILD_SHA, computed in crates/postgres/build.rs by hashing every file under crates/, services/ and review-definitions/, plus Cargo.toml, Cargo.lock and an optional DEEPREF_BUILD_SHA. A fix to an unrelated HTTP route, a test, or a dependency bump changes the hash. A calibration is therefore valid for exactly one build.

This is safe but unworkable: a calibration that takes weeks to earn would be voided by the next deploy.

Gap C. Pass/fail is a label, not a computation

status is set by whoever inserts the row. thresholds, metrics and reviewer_metadata are only required to be JSON objects; nothing checks them, and nothing records who approved. “Expert-adjudicated” lives in the docs, not the code. The existing metric engine (crates/ai/src/evals.rs) computes sensitivity, specificity and a 20:1 weighted loss, but needs a baseline-vs-candidate pair plus numeric-extraction and citation cases, and has no confidence intervals. It is not connected to the bundle table.

Gap D. One bundle cannot cover both stages as written

Bundles are keyed by definition_key='screening' for both stages. But title/abstract uses model profile Reasoning and full-text uses LongContextReasoning (execution.rs), and the profile is part of the model identity, so the two stages probably hash differently. The sweep picks the single newest passing bundle regardless of stage. Two bundles would therefore likely knock each other out. I did not execute this; verify with a test before relying on it.

Asset E. Useful building blocks already exist

reviewer_agreement in ai_reviewer.rs already computes human-vs-AI agreement and Cohen’s kappa per stage using the human’s decision before any conflict was settled (human_decision_before). It is exposed through autonomy.rs. The project also has screening_events with actors, an ai_budget, and the sweep scaffolding to reuse.

UX F. The banner can lag and is a dead end

calibration_stale is only reported after the sweep has hit a refusal and written second_review_gate, so right after a deploy the status can still read “automatic”. The banner names no action and no owner. Whatever strategy you pick should give it a button.

2. Five ways to calibrate

How it works

Draw a random sample from project_reports with a stored seed and freeze it. Two reviewers screen it blind (nobody sees the AI or each other). Disagreements are adjudicated, which gives the gold standard and a human-human kappa. The AI runs on the same records under the exact current hash. If recall clears the threshold, the owner approves and a bundle is written. This is also what Cochrane guidance asks for anyway: pilot the criteria on a sample before full screening, with at least two independent screeners.

Risks

  • Includes are rare. At 5% prevalence, 60 includes needs 1,200 records (30 h); at 2% it needs 3,000 (75 h). That cost falls on the people the AI is meant to relieve.
  • Any later hash change (see B above) throws the pilot away.
  • Pilot records are screened twice by humans and then screened again in the normal flow unless excluded from it.

What it needs in the product

  • Data: new tables for a frozen sample, per-reviewer blind labels, and adjudication (not screening_state, which is single-reviewer state and must not be polluted). Reuse project_reports, reports.
  • Runs: a new ReviewOrigin variant for calibration runs (amends ADR 0004: ungated, writes nothing to ai_reviewer_decisions). Take the hash from the manifest the run built.
  • Metrics: a screening-only entry point next to crates/ai/src/evals.rs, adding exact binomial intervals, keeping the “maybe counts as retained” semantics.
  • API/UI: routes beside routes/autonomy.rs to draw, label, view results and approve; a calibration page; banner button. Approval calls insert_review_calibration_bundle with metrics, CI, reviewer ids and the adjudicator.

How it works

Store an EvaluationSet (the JSON format already used by reviewed-small-v1.json) with a few hundred real, adjudicated screening cases. Run it against the live route in CI or on a schedule. It proves the model, parser and prompt work well in general, and gives a regression alarm when the provider changes.

Risks

  • It cannot say anything about a specific project’s criteria. A model that screens well on cardiology reviews can still misread a niche protocol.
  • As built, the gate binds a bundle to project_id and to the protocol in the hash, so a platform-level result would not satisfy it without a design change.
  • Public datasets (for example CLEF TAR, SYNERGY; not reviewed here) have their own labelling noise and may be in the model’s training data.

What it needs in the product

  • A screening-only evaluation entry point (the current gate also demands numeric-extraction and citation cases, and a baseline model).
  • A platform-level record (project-less bundle table or nullable project_id) and a rule such as “the gate needs both a current platform pass and a project-level pass”. This turns B into a prerequisite, not a substitute.
C

Shadow-mode warm-up

The AI runs as a silent second reviewer on records the humans have already decided; metrics accumulate until the threshold is met.
Recommended
RecordsWhatever humans screen anyway; gate checks start at 60 includes

How it works

Once a human has decided a record, the sweep also runs the AI on it in a new “shadow” origin. The result goes into an observations table, not into ai_reviewer_decisions, so nobody is anchored and nothing becomes a conflict. For each observation the system stores the hash it ran under. A checkpoint job (every +20 includes after 60) computes sensitivity with an exact interval, specificity, abstention rate, kappa and conflict rate. When it passes, the owner sees “AI second review is ready to switch on” with the numbers, approves, and a bundle is inserted.

Risks

  • The reference is one human. A single experienced title/abstract screener misses a median of 5% of eligible studies (range 0% to 58%; 13% for less experienced screeners; Waffenschmidt 2019). Where the human missed and the AI found it, the AI is scored as a false positive. Mitigation: also report AI recall on records that ended up included after full-text screening, which is the better reference.
  • Repeated looks inflate the chance of a lucky pass. Use fixed checkpoints and a minimum of 60 includes; this is not a formal sequential design.
  • Hash changes mid-warm-up reset the count (see B); resolve that first.
  • The gate text says “expert-adjudicated”; here the adjudication is the owner’s approval, which needs an explicit ADR note.

What it needs in the product

  • Data: second_review_observations(project_id, report_id, stage, semantic_bundle_hash, ai_decision, human_decision, final_inclusion, run_id). Human side comes from screening_state and screening_events.
  • Worker: a second pass in sweep_second_reviews (same batch cap, ai_budget check and attempt table pattern), picking decided records instead of waiting ones.
  • Metrics: reuse the kappa code in ai_reviewer.rs; add the interval and the sensitivity query; write the bundle via insert_review_calibration_bundle with reviewer_metadata naming the approver.
  • UI: a calibration progress card on the screening pages (“37 of 60 includes observed”) replacing the dead-end banner, plus an approve button for the owner.

How it works

The owner ticks a logged acknowledgement (“this AI reviewer has not been validated on this protocol”) and picks a scope: title/abstract only, a daily cap, and every AI opinion labelled “unvalidated” in the conflict view. The override auto-expires after N days or M records, and ends immediately if monitoring (E) shows poor agreement.

Risks

  • Weakest methodologically. The joint Cochrane, Campbell, JBI and CEE statement expects users to show AI use does not compromise rigour, and says synthesists may need to pilot or calibrate a tool within their own synthesis.
  • In second-reviewer mode an AI miss does no direct harm when the human includes, but the human may defer to the AI in conflicts (automation bias), and reviewers will not read “unvalidated” labels forever.
  • Contradicts the ADR 0004 “fail closed” stance; needs an ADR amendment.

What it needs in the product

  • Do not reuse review_calibration_bundles with a fake “passing” status. Its status check allows only passing and failed, and a faked row would be indistinguishable from real evidence in the audit export (audit_export.rs). Use a separate review_gate_overrides table (who, when, scope, expiry, text of the acknowledgement) and a distinct admission origin.
  • Include the override in the audit export and in any methods-section text DeepRef generates.

Continuous monitoring and automatic recalibration

Recommended with C

How it works

After approval, every resolved human-vs-AI pair keeps feeding the same metrics (conflicts already store human_decision_before, so the independent human opinion is preserved). If the rolling lower bound on sensitivity falls below a floor, or kappa collapses, the gate closes with a new refusal reason (calibration_degraded) and the banner says why. When the hash changes for any reason, the system flips the project back to shadow mode (C) automatically instead of just showing “stale”.

Risks

  • After the gate opens, humans resolve conflicts with the AI’s opinion visible, so later pairs are not independent. Keep measuring on the pre-resolution decision (already stored).
  • Rolling windows on rare includes are noisy; use the same interval math, not raw percentages.
  • Auto-pause can interrupt a team mid-screening; the notice must say what to do.

What it needs in the product

  • Extend the second_review_gate.refusal check (migration 0040 allows only calibration_stale) with calibration_degraded and recalibrating.
  • On the stale path in sweep_project, switch the project to shadow collection instead of stopping. Notify the owner through the existing notifications feature.

3. Recommended thresholds and sample sizes

For a second reviewer, the metric that decides whether a record is lost is sensitivity (recall) on true includes. A false include only adds a conflict for a human to settle. Specificity therefore affects workload, not safety.

The number that matters is the count of true includes, not total records. Recall is estimated from includes only, so with 5% prevalence you need 20 records to see one include.

Proving a 95% lower bound is expensive (about 60 includes with zero misses, 124 with two). A 90% lower bound with a 95% point estimate is affordable and, for a second reviewer, defensible.

Proposed gate rule (for screening, per stage)

  • Minimum evidence: at least 60 true includes observed under the current hash, and at least 300 records in total.
  • Sensitivity: point estimate at least 95% and one-sided 95% lower bound at least 90%. At 61 includes this allows at most 2 misses (3 misses in 60 gives a lower bound of 87.6%, a fail).
  • “Maybe” handling: keep the existing semantics (maybe retains the record, counts as abstention, never as a false negative).
  • Specificity: report, do not gate. Optionally warn below 60%, where conflicts would swamp reviewers. Report the conflict rate directly; it is what users feel.
  • Kappa: report AI-human kappa and compare to the human-human kappa where a pilot exists. Treat as a soft warning, not a hard gate (see below).
  • Checkpoints: evaluate at 60, 80, 100 includes and so on, not after every record.
  • Existing gate flags: max_false_negative_rate of 0.0 in the test fixture is a regression oracle for six toy cases. Do not copy it into production thresholds.

Kappa: how to read it

KappaLandis & Koch label
below 0Worse than chance
0.00 to 0.20Slight
0.21 to 0.40Fair
0.41 to 0.60Moderate
0.61 to 0.80Substantial
0.81 to 1.00Almost perfect

McHugh (2012) argues these bands are too lenient for health research. Kappa also drops sharply when includes are rare, even with high raw agreement, and an over-inclusive but safe reviewer scores low. That is why it is reported, not gated.

What the literature says about LLM screeners. Results vary widely by model, prompt and review. A 2025 meta-analysis reports pooled sensitivity and specificity near 90% across 14 LLM-based tools (Kim et al.); a pre-registered GPT-4 study found performance dropped a lot after correcting for chance agreement and class imbalance, with “human-like” results only for full-text screening with well-designed prompts (Khraisha et al.); and zero-shot LLM studies show that choosing the decision cutoff to hit a target recall is what makes them usable (Wang et al.). The lesson for DeepRef: measure per project and per build, do not inherit a published number.

The Z.AI to OpenCode Go switch

What the code does now

The provider label "zai" is hard-coded in crates/http-api/src/lib.rs and services/worker/src/lib.rs, and is written into ai_model_routes.provider by ensure_default_model_routes (ai_usage.rs). That function inserts routes only when no enabled route exists for a profile, and sets model_version equal to the model name.

Does it invalidate calibrations?

Only if the identity changes, and that is the trap. New route rows labelled opencode-go change the hash: calibrations go stale (correct). But if someone only changes ZAI_BASE_URL and keeps label and model name, the hash is unchanged and a calibration made on Z.AI would silently keep admitting runs on a different serving stack.

In practice, today no project has a calibration (finding A), and the code change for the switch also changes the build hash (finding B). So nothing real is lost now, but the policy should be fixed before the first calibration exists.

Recommendation: treat any provider change as a new model identity, even with the same model name. A host can differ in quantization, context limit, default sampling, safety filtering or rate-limit behaviour, and DeepRef cannot see that. Relabel the provider, disable the old routes, and let the new route start a fresh warm-up. Do the switch before starting calibration (C) so the first evidence is collected on the stack you will keep.

5. Recommended path

Shadow-mode warm-up, owner approval, then continuous monitoring. Pilot sets stay available as an opt-in for teams that want proof before their first screened record.

  1. Phase 0, fix the foundations (S, about 2 days). (a) Decide and implement what the runtime identity covers (decision 6). (b) Make the bundle lookup stage-aware (finding D) and add a test that two bundles coexist. (c) Settle the provider-label rule and do the OpenCode Go switch first. (d) Replace the banner copy with the actual state and owner action.
  2. Phase 1, shadow-mode calibration (C, M). Observations table, shadow origin, checkpoint metrics with exact intervals, owner approval screen, bundle insert. Title/abstract first; full-text later, because full-text includes arrive later and need their own evidence.
  3. Phase 2, monitoring and auto-recalibration (E, M). Rolling metrics, the calibration_degraded and recalibrating refusals, owner notifications.
  4. Later, optional. The pilot set (A) for projects that want to start earlier, and a benchmark set (B) as a release-time regression alarm for the model and prompt. Skip D unless a deadline forces it, and then only time-boxed and logged.

Why this order

  • No extra human work. A and B spend expert hours on records that would be screened anyway; C reuses decisions the team makes regardless.
  • Evidence is project- and build-specific. That is exactly what the hash demands, and what the position statement of Cochrane, Campbell, JBI and CEE implies when it says tools may need to be piloted or calibrated in the synthesis at hand.
  • Safety does not depend on the gate alone. In second-reviewer mode the AI cannot exclude anything; the human decision stands unless a person resolves a conflict. The gate protects against wasted reviewer attention and automation bias, and keeps the audit story clean.
  • The cost is delay. At 5% prevalence the AI starts contributing after roughly 1,200 human-decided records. For a 4,000-record search that is 30% of the title/abstract work. If that is too slow, run a small pilot (A) on 300 records alongside, or accept D for a short, logged period.

Caveat: single-human reference decisions understate how good the AI is where it finds studies the human missed, and overstate it where the human and AI make the same mistake. The full-text-included reference reduces the first problem but not the second.
