Decision-complete implementation plan

DeepRef Production Platform Migration

A production-first AWS, EKS, OpenTofu, Argo CD, Cloudflare Access, NATS, Neo4j, and PostgreSQL architecture replacing the supported self-hosting model.

AWS sa-east-1 Three isolated accounts 99.9% core SLI Greenfield launch

Summary

Replace the distributable self-hosting setup with a production-focused AWS platform:

  • Three isolated AWS accounts—development, staging, and production—in sa-east-1.
  • OpenTofu-managed three-AZ VPCs, EKS 1.36 clusters, RDS PostgreSQL 17, ECR, IAM, KMS, backups, budgets, and observability.
  • Argo CD-managed application workloads, NATS JetStream, Neo4j Community, Cloudflare Tunnel, secrets synchronization, and telemetry collectors.
  • Cloudflare Access protects every environment using membership in the configured GitHub organization, with no application-level user or tenant model.
  • PostgreSQL remains authoritative; Neo4j is an asynchronous, rebuildable graph read model.
  • Core target: 99.9% monthly availability, PostgreSQL RPO ≤5 minutes and RTO ≤60 minutes for service or AZ failures. Total regional loss is outside this target.
  • Greenfield production launch with no self-hosted data migration.
  • Initial envelope: tens of team users, 250,000 works, and 2.5 million citation edges.

The graph tier is intentionally rebuildable. Neo4j Community is single-node, and a graph outage degrades graph and recommendation features without taking down core project and ingestion workflows.

Verified platform references: AWS EKS lifecycle, NATS Kubernetes deployment, JetStream clustering, and Neo4j editions.

Execution and Git workflow

  1. Start implementation from a clean, current development branch:
git fetch origin
git switch development
git pull --ff-only
git switch -c feature/production-platform
  1. Keep all source, IaC, Helm, workflow, and documentation changes on that feature branch.
  2. Promote through feature/production-platform → development → staging → main.
  3. Retain hotfix/* → main, followed by back-merges to staging and development.
  4. Create a protected orphan gitops branch during platform bootstrap. It contains environment values and immutable release locks only.
  5. Add just feature <slug> to validate a clean worktree, update development using a fast-forward-only pull, and create feature/<slug>.

Agent allocation

  • Sol xhigh remains the planner, integrator, and orchestrator.
  • Requested Luna models are unavailable in the current runtime. Exploration used gpt-5.6-terra medium; implementation uses Luna xhigh if available, otherwise Terra xhigh.
  • Independent workstreams cover Rust correctness/projection, AWS/OpenTofu/EKS, and CI/DX/documentation.
  • Sol high reviews every phase and conducts the final production-readiness audit.
  • Subagents receive non-overlapping file ownership and return changes to the orchestrator for integration.

1. Correct the application before scaling

Production deployment is blocked on the following correctness work:

  • Replace check-then-act event deduplication with atomic transactional claims.
  • Add renewable DOI work leases with owner, expiry, attempts, and stale-lease recovery.
  • When a DOI is cached, attach its existing work and references to the requesting project instead of skipping it.
  • Persist fetched work, citations, discovered children, terminal state, processed-event marker, and outbox events in one PostgreSQL transaction.
  • Insert discovered children before evaluating ingestion completion.
  • Acknowledge NATS messages only after the database transaction commits.
  • NAK retryable failures with bounded backoff; send malformed or exhausted messages to the DLQ and terminate delivery.
  • Replace per-process Crossref throttling with a PostgreSQL-backed global provider rate limiter.
  • Reconcile expired claims, nonterminal ingestion items, unpublished outbox rows, and lost JetStream work.
  • Gracefully stop pulling and drain active work before termination.

Rust boundaries

  • Extend crates/events with versioned domain events.
  • Extend crates/graph into a typed Neo4j repository interface.
  • Add services/projector for PostgreSQL-to-Neo4j projection and graph metrics.
  • Add an API migrate subcommand for the one-shot migration Job; normal API startup never migrates.
  • Use typed library errors, contextual service errors, minimal visibility, and no production unwrap().

2. Durable events and graph projection

Replace the broad default stream with explicitly provisioned streams:

StreamPurposeProduction policy
DEEPREF_WORKFetch requestsWork-queue retention, three replicas
DEEPREF_DOMAINGraph and metric changesLimits retention for 30 days, three replicas
DEEPREF_DLQPoison and exhausted events90-day retention, three replicas

Applications receive publish and consume permissions only. GitOps owns stream and consumer creation.

Event envelope

  • schema_version, deterministic event_id, event_type, and occurred_at
  • producer, correlation_id, and causation_id
  • Entity type, key, monotonic revision, and typed payload

Create entity-level events for work, project membership, citations, unresolved references, deletion tombstones, and metric recomputation. Revision columns and a database sequence prevent out-of-order events from overwriting newer graph state.

Projector behavior

  • Process events idempotently.
  • Apply graph mutations and processed-event markers in one Neo4j transaction.
  • Maintain entity projection cursors so stale upserts cannot resurrect deleted or superseded data.
  • Publish projection completion and failure metrics.
  • Compute graph metrics in Neo4j and write the latest snapshots back to PostgreSQL.
  • Expose projection lag and the last successful revision.

Move Neo4j constraints and indexes into versioned projector migrations.

3. Graph degradation and rebuild

PostgreSQL remains the recovery authority. Neo4j Community runs as one StatefulSet with encrypted gp3 storage.

During Neo4j failure:

  • Projects, article metadata, ingestions, and settings stay available.
  • Graph and recommendation routes return 503 GRAPH_UNAVAILABLE with Retry-After.
  • Cached article metrics stay readable but are marked stale.
  • The UI presents a graph-specific degraded state.

Rebuild Job

  1. Acquire a PostgreSQL advisory lock and mark projection status as rebuilding.
  2. Start a repeatable-read snapshot and record the graph revision watermark.
  3. Pause normal projection.
  4. Clear Neo4j and recreate constraints.
  5. Bulk-load projects, works, memberships, citations, unresolved references, and cached metrics in bounded batches.
  6. Replay domain events newer than the watermark.
  7. Verify counts and sampled deterministic hashes.
  8. Mark the projection ready and resume consumption.

The complete rebuild must process 250,000 works and 2.5 million edges in under 60 minutes.

4. API, configuration, and frontend

HTTP API

  • GET /health/live — process liveness only.
  • GET /health/ready — PostgreSQL and schema compatibility; NATS/Neo4j degradation does not remove the core API.
  • GET /health/dependencies — PostgreSQL, NATS, outbox, worker lag, Neo4j, and projection status.
  • GET /projects/{project_id}/projection — state, revision, lag, last success, and last error.
  • Keep /health as a deprecated alias for one release.
  • Change metric recomputation to 202 Accepted and enqueue a versioned event.

Introduce ApiErrorBody, DependencyStatus, ProjectionStatus, and ProjectionMetadata. Article responses gain metrics_as_of and metrics_stale; graph responses include projection metadata. Add pagination and response-size limits to unbounded endpoints.

Runtime configuration

Add APP_ENV=local|development|staging|production. Local defaults are allowed only for local; hosted services fail fast when required values are missing.

  • PostgreSQL URL or secret file and bounded pool settings
  • NATS URL, credentials, CA, consumer, and timeout settings
  • Neo4j URI, credentials, database, and query timeout
  • OpenTelemetry endpoint, service version, environment, and shutdown deadline
  • API bind address and exact CORS origins where applicable

Until a valid Crossref mail address is configured, ingestion creation returns a typed configuration error.

Svelte application

  • Keep the SPA and same-origin /api contract.
  • Handle typed dependency failures through TanStack Query.
  • Add dependency banners and graph/recommendation degraded states.
  • Keep core project and ingestion screens usable during graph recovery.
  • Do not add application users, organizations, or tenant ownership.
  • Use Svelte 5 runes and validate every changed component with the Svelte autofixer.

Create immutable web, API, worker, and projector images. The API image also runs the migration subcommand.

  • Build once per Git tree hash and pin every base image by digest.
  • Run as non-root with read-only filesystems, dropped capabilities, RuntimeDefault seccomp, and explicit temporary mounts.
  • Add OCI source, revision, and version labels.
  • Add resource requests, limits, probes, and termination grace periods.
  • Produce SBOMs, vulnerability reports, provenance, and keyless signatures.

7. AWS and Cloudflare IaC

Use reusable infra/modules and explicit infra/environments/{development,staging,production,global} roots. Do not use OpenTofu workspaces for environment isolation.

Per-account AWS resources

  • Three-AZ VPC with private workload and data subnets.
  • One NAT gateway in development; one per AZ in staging and production.
  • VPC endpoints for ECR, S3, STS, CloudWatch, Secrets Manager, and SSM.
  • Private EKS 1.36 with control-plane audit logs, access entries, EBS CSI, Pod Identity, and managed node groups.
  • Three fixed stateful nodes in staging and production; one in development.
  • Autoscalable stateless node groups without Karpenter initially.
  • Separate RDS PostgreSQL 17 instances: Single-AZ development/staging and encrypted, deletion-protected Multi-AZ production with 35-day PITR.
  • Immutable ECR repositories, scanning, lifecycle policies, and cross-account promotion roles.
  • KMS, Secrets Manager, least-privilege IAM/Pod Identity, Backup Vault Lock, budgets, and SNS alarms.
  • An SSM administration host or VPC-connected CodeBuild runner for private-cluster bootstrap and break-glass work.
  • Per-environment S3 state with KMS encryption, versioning, lifecycle protection, account preconditions, and native lockfiles.

OpenTofu documents use_lockfile=true as the preferred native S3 locking mechanism.

Ownership boundary

OpenTofu owns AWS infrastructure, global Cloudflare/GitHub resources, secret containers, observability resources, and the initial Argo installation. Argo owns namespaces, workloads, NATS, Neo4j, External Secrets, policies, and collectors. No resource is managed by both.

Cloudflare perimeter

  • deepref-dev.<base_domain>
  • deepref-staging.<base_domain>
  • deepref.<base_domain>

Run one cloudflared replica in development and two fixed replicas in staging/production. Connections are outbound-only; there is no public AWS load balancer or bypass hostname.

References: Cloudflare Kubernetes Tunnel, tunnel availability, and GitHub identity provider.

8. GitOps, CI/CD, and promotion

Source branches hold application code, chart source, and IaC. The gitops branch holds only environment values, release locks, and Argo root/ApplicationSet definitions.

Each release lock records source commit, Git tree hash, chart version and digest, every image digest, migration version, and creation time.

Delivery flow

  1. A development merge runs all checks, builds each image and chart once, signs and attests them, and records a tree-hash release manifest.
  2. A deployment GitHub App opens deploy/dev/<tree-hash> → gitops, changing only the development lock. Policy checks allow automatic merge.
  3. Staging promotion verifies the source tree matches a tested development release, copies exact OCI manifests into staging ECR without rebuilding, and opens the staging deployment PR.
  4. Staging requires one approval.
  5. Production repeats from the deployed staging release and requires two approvals plus GitHub production-environment approval.
  6. Argo auto-syncs only after the approved lock reaches gitops.
  7. Rollback is a protected GitOps PR pinning the previous migration-compatible release.

Repository policy

  • Retain one approval for development and staging, two for main.
  • Enforce admins, stale-review dismissal, last-push approval, conversation resolution, and no force pushes or deletions.
  • Add CODEOWNERS for IaC, workflows, charts, migrations, and production locks.
  • Restrict gitops writes to the deployment GitHub App.
  • Use squash merges for feature PRs and merge commits for long-lived branch promotions.

CI additions

  • Cached Rust and web checks, audits, codegen drift, and full-stack integration/E2E tests.
  • OpenTofu format, validation, TFLint, native tests, and speculative plans.
  • Helm lint/template, kubeconform, policy tests, and server-side dry runs.
  • ShellCheck, actionlint, workflow security analysis, and pinned action SHAs.
  • Container scanning, SBOM, provenance, signatures, and admission verification.
  • Trusted-branch infrastructure applies through GitHub OIDC and protected environments only; no static AWS keys.

9. Observability, SLOs, and operations

Instrument API, worker, projector, PostgreSQL, NATS, and Neo4j with structured JSON logs and OpenTelemetry correlation.

  • CloudWatch Logs with 7/30/90-day development/staging/production retention.
  • Amazon Managed Prometheus and Managed Grafana.
  • ADOT and X-Ray-compatible traces.
  • Encrypted SNS topics with confirmed recipients.
  • CloudWatch Synthetics through Cloudflare Access using a rotated service token.

Dashboards and alarms cover HTTP RED signals, core and graph SLIs, RDS failover/saturation, NATS quorum and lag, DLQ depth, worker leases and retries, outbox age, projection lag, Neo4j availability, Kubernetes health, tunnel replicas, certificates, and budget thresholds.

Add runbooks for bootstrap, promotion, rollback, migration failure, RDS failover/PITR, NATS quorum and DLQ recovery, Neo4j rebuild, projection lag, Cloudflare or IdP outage, credential rotation, node/AZ drain, and break-glass access.

Test and acceptance criteria

  • Existing Rust and web checks remain green.
  • A new developer installs tools, starts dependencies, and runs every service through the documented mise/just workflow.
  • Tests cover claims, lease recovery, rollback, idempotency, cached-work attachment, ingestion completion, event compatibility, and global throttling.
  • Crashing a worker at every fetch, commit, publish, and ack boundary loses no child work and creates no duplicate logical facts.
  • Malformed and repeatedly failing events reach the DLQ after bounded delivery.
  • Killing one NATS pod preserves quorum and processing.
  • Stopping Neo4j preserves core operations and produces typed graph-only degradation.
  • The representative graph rebuild completes in under 60 minutes with count/hash parity.
  • A failed migration blocks rollout while the previous application continues serving.
  • RDS Multi-AZ failover and PITR drills meet the declared RPO/RTO.
  • Exact signed image and chart digests progress through all three environments.
  • Unsigned or unapproved images are rejected.
  • A nonmember GitHub identity is denied and no public AWS origin path exists.
  • Rollback restores the previous compatible release through a GitOps PR.
  • tofu plan is empty after apply and Argo reports every application healthy and synced.
  • Documentation contains no supported self-host deployment path.

Assumptions and apply-time prerequisites

  • The three AWS accounts already exist; the repo creates their VPCs, EKS clusters, and workload resources.
  • An AWS SSO administrator performs one privileged bootstrap per account to create or migrate the encrypted state backend and GitHub OIDC trust.
  • Required inputs: AWS account IDs, Cloudflare account and zone IDs, base domain, GitHub OAuth credentials, deployment GitHub App credentials, GitHub organization/team, operations email, admin CIDRs, and monthly budgets.
  • SNS alerting is not operational until the recipient confirms the subscription.
  • No production data import is required.
  • All users admitted by Cloudflare have equal application privileges, including settings access.
  • Neo4j Community is single-node and rebuildable; graph availability is excluded from the core 99.9% SLI.
  • The RPO/RTO target excludes total sa-east-1 loss.
  • Development Compose is a local tool, never a supported self-hosting option.
